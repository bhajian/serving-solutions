**What you get:** scrape configuration for frontends, workers and the Planner, alert rules
and a Grafana dashboard built on the metrics the benchmark harness already scrapes, and an
end-to-end canary through the gateway. **What you still own:** kube-prometheus-stack
(release `prometheus` in `monitoring`), Alertmanager routing, and the SLO values.

| File | Contents |
| --- | --- |
| [podmonitors.yaml](podmonitors.yaml) | Frontend (`http`, 8000), workers (`system`, 9090) and Planner (`metrics`, 9085), selected by `nvidia.com/dynamo-component-type` and relabelled with `dynamo_namespace` (the Planner filters on it), `graph` and `component_type` |
| [rules.yaml](rules.yaml) | Multi-window p99 TTFT/ITL SLO burn; no workers; decode without prefill; prefill host memory > 70% of limit; NIXL bootstrap latency and backlog; queue growth per pool; KV pool exhaustion and retractions; InfiniBand errors; GPU XID; failing canary |
| [dashboards/dynamo-serving.json](dashboards/dynamo-serving.json) | TTFT/ITL/TPOT, output tokens/s, queue depth per pool, KV usage and hit rate, NIXL latency/bytes/bandwidth, registered workers, IB bytes and errors, DCGM, prefill memory, engine-side ITL. Delivered as a ConfigMap labelled `grafana_dashboard: "1"` for the Grafana sidecar |
| [canary/](canary/) | Per-model CronJob: one 4-token chat completion through `https://<model>.<INFERENCE_DOMAIN>` every 5 minutes; `DynamoCanaryFailing` alerts on failed jobs. Needs a `canary-token` Secret |

If the dynamo-platform chart's own PodMonitors are enabled, keep one set of scrape
configuration to avoid duplicate series.
